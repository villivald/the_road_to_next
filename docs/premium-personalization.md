# Premium personalization

Implemented 24 October 2026. Prices remain €2/month and €15/year; billing and
subscription behavior are unchanged.

## Design approach

The 25 October revision combines recognizable occasions with two general styles.
[Paperless Post](https://www.paperlesspost.com/cards/group/baby-shower-invitations?page=1)
organizes its library by occasion, theme and style; [Canva](https://www.canva.com/virtual-invitations/templates/)
also uses occasion names and matching visual sets. For this small catalog, all
choices stay visible in two groups instead of adding filters or tabs. Plain labels,
recognizable thumbnails and an immediate preview follow
[NN/g's guidance on recognition, familiar concepts and consistency](https://www.nngroup.com/articles/ten-usability-heuristics/).
These are design decisions informed by those references, not a claim of user-test results.

One artwork and palette per theme carries through tiles, list headings and PNGs.
Patterns stay separate from text and QR codes; the app's typography and controls
retain their existing style in both color schemes.
The four generated occasion patterns are the selected design. The archival
comparison is a private local preview and is not part of the shipped app.

## User controls

- **Create list / List settings → List theme:** Classic is free. Premium adds
  four occasion designs—Christmas, Birthday, Baby & kids, and Love—and two everyday
  styles, Botanical and Waves. Choices are grouped, all visible and keyboard-accessible,
  with a live preview. The occasion patterns use a coordinated printed-paper style;
  the everyday patterns come from Shin-Bijutsukai (1902). Sources and generation
  prompts are in `public/illustrations/themes/README.md`. Themes appear on list
  headings, Browse/Favorites/My lists previews, authorized guest views and sharing
  cards. Existing uploaded images are preserved.
- **Open a list → Sharing card → Download sharing card:** an administrator of a published list can
  download a 1200 × 800 PNG with its title, matching design and QR code. The same
  download is available in **List settings → Download a QR sharing card**. The list
  owner's Premium pays for this feature, including for other administrators.
- **Account → Profile:** “Show a Premium badge on my public profile” is opt-in.
  The badge appears beside the profile name in People and saved People only while Premium is active.
  Existing profile discoverability rules still apply.
- **Premium page:** interactive theme examples, localized example cards, badge
  preview, plan comparison and the existing renewal/payment disclosures.

List covers are small thumbnails beside the title (up to 144 × 108 CSS pixels at default text size),
including in guest view. Wish images retain their existing size. Theme artwork
forms a shallow decorative strip above the heading; text stays on a plain surface.

The existing stored theme IDs remain stable: `festive` → Christmas, `minimal` → Waves,
`birthday` → Birthday, `wedding` → Love, `playful` → Baby & kids. Only the catalog
labels and artwork changed, so existing choices need no data conversion.

Both interface languages and light/dark modes are supported. Cards use fixed,
print-friendly colors, independently of the device's light/dark preference.

## Access and expiry

The server validates theme identifiers and enforces the list owner's entitlement.
A selected theme survives expiry and ownership transfer. Editing other list details,
keeping the same theme, or returning to Classic stays available without Premium.
Choosing a different Premium theme or downloading another card requires active
Premium for the current owner. Existing private-list access rules remain unchanged.

The badge preference is retained after expiry, but the public badge disappears.
It returns when Premium becomes active again unless the user hides it. Hiding is
always available; newly enabling the preference requires Premium. Discovery and
Favorites calculate badge visibility in their existing batched queries.

## Sharing-card privacy and operation

`GET /api/lists/:id/sharing-card?locale=en|fi` requires a verified, unexpired session,
current list administrator membership, publication, and active owner Premium.
Permissions and card metadata are checked again after rendering. Removed access,
a revoked session, an expired grant, or an unpublished/changed list prevents sending
the generated bytes. Responses are private/no-store; previews and downloads share
a limit of 20 requests per user per hour.

The QR code contains the ordinary localized list URL. It never contains a guest
token or grants access to a private list. Private cards explicitly warn that they
include the list title and that recipients need existing list access. No wishes,
reservation details, owner identity, uploaded images or email addresses are drawn.
A previously downloaded image is a static copy: changing/deleting the list cannot
recall it. The destination still checks current access whenever opened.

Rendering runs only when a manager opens the sharing-card dialog, requests an
inline preview, or downloads a card, using Sharp, local font outlines and a local QR
encoder. The preview displays the actual PNG, including the QR code. Classic cards
use botanical artwork with their original warm paper palette. It makes no external image/font requests, creates no saved media
and adds no scheduled jobs. Rendering libraries are loaded only after authorization.
Next.js traces both font files and the six local WebP illustrations into the route's
deployment bundle. Public example cards use content-hashed static imports, so
updated designs are not held behind old image-optimizer cache URLs. Their QR
codes open the Premium page.

## Database and release

New additive migration: `20261024000100_premium_personalization`.

- `Wishlist.theme`: defaults to `classic`; database constraint limits valid themes.
- `User.showPremiumBadge`: defaults to `false`.

The migration was applied to the local development and isolated test databases.
Production has not been migrated or deployed for this change. Before release:

1. Review the changes and verify the production database host/name using the
   dedicated production environment. Do not use the local development URL.
2. Run `prisma migrate status`, then `prisma migrate deploy`, with that verified
   production environment. Apply this additive migration before deploying the code.
3. Deploy the reviewed commit. No new environment variables or provider settings
   are required; `APP_URL` must remain the intended canonical HTTPS origin.
4. As a Premium list owner, save a theme, download a PNG, scan its QR and toggle
   the badge. Check a Free account cannot select a new Premium theme or download
   cards. Check a private card does not grant a visitor access.

## Verification

Regression tests cover owner-paid authorization, expiry/reset behavior, private and
revoked guest access, badge opt-in/expiry, and download revocation during rendering.
PNG titles wrap at word boundaries and shrink moderately to fit long Finnish
compound words. Text stays on plain paper; artwork occupies a side strip, separated
from the QR code and its white quiet zone.

PNG tests decode every theme's QR with an independent decoder and check untrusted
long titles, Finnish characters, no external requests and complete caption output.
Browser checks exercise settings/save/reload/download, public badge opt-in/out, and
EN/FI Premium examples with light/dark styles and accessibility/overflow assertions.
See `tests/personalization.integration.test.ts`,
`tests/premium-personalization.test.ts` and `e2e/personalization.spec.ts`.

The final review removed a redundant badge sample from the profile checkbox: it
overflowed at 320px with 200% text. The actual public profile badge remains beside
the person's name. Existing English/Finnish reflow tests cover the corrected form.
Dependency patches and their compatibility overrides are documented in
[dependency maintenance](dependency-maintenance.md).

Final validation on 25 October: code/style/format/type checks, 167 unit tests,
288 isolated database tests and 306 browser cases pass (258 Chromium desktop/mobile,
48 Firefox/WebKit). Production builds pass; both fonts and all six theme images are
present in the download route's file trace. English/Finnish showcase PNGs match the
renderer pixel-for-pixel and their QR codes open `https://wishlist.fi/premium`.
The dependency audit reports zero vulnerabilities. Real-device checks remain the
previously agreed manual release follow-up.

## List-page usability follow-up (26 October)

New-list forms state prominently that lists start hidden. List managers can now
show or hide a list directly on its page, with its audience and the reservation
effect stated beside the control. The existing settings control and server-side
publication/access rules remain in use.
Hiding asks for confirmation before ending reservations; showing stays one click.

Visibility is part of the list header's toolbar, alongside the sharing-card and
settings controls, rather than a separate bordered bar. Its status and action
sit together, with one contextual explanation below. The action retains a 44px
minimum tap target and the reservation warning stays visible. Text and controls
wrap on narrow screens and with enlarged text.

Visibility changes use one temporary confirmation, without inserting a success
box into the header. See [UI feedback](ui-feedback.md) for message timing,
dismissal and accessibility behaviour.

Free list managers can preview real Birthday, Christmas and Botanical sharing-card
examples in English/Finnish. Preview choices do not save a theme, grant access or
enable downloads. The examples' QR codes open the Premium page; actual downloads
continue to require a published list and the owner's Premium access.
Hidden Premium lists retain their own preview without an incorrect upgrade
prompt. Hidden free lists explain both requirements: show the list and have
Premium access. The download endpoint still rejects hidden lists.

The four additional sample PNGs use the production renderer. Recreate them with
`node --import tsx scripts/prepare-sharing-card-examples.ts` from the repository
root. This performs no database or provider operations. No migration or new
configuration is needed for these UI changes.

Promo-code entry during onboarding is a separate design decision. Redemption must
remain verified-email-only and rate-limited. An optional signup field would need
secure carry-over through verification and must not make an invalid promo block
account creation. The signup and redemption flows are unchanged in this follow-up.

Final audit: ESLint, Stylelint, Prettier, TypeScript, 167 unit tests, 288 tests with
database integration enabled and production builds pass. The full 276-case
Chromium suite passed, followed by 28 checks of the final sharing-card/layout
fixes. All 34 Firefox/WebKit cases are covered successfully; the six feedback
cases were rerun after correcting an expiry test that left the pointer hovering
over the toast.

Visual and accessibility checks cover EN/FI, light/dark, 320px layouts, 200% text,
keyboard focus, reduced motion, preview images and QR destinations. Real-phone
and screen-reader testing remain manual follow-ups. The final audit also moved
download requirements above the preview, reduced narrow-dialog padding and
fixed the timer for repeated guest-link copies. No remaining blocking issue was
found. These changes are local, uncommitted and undeployed.
